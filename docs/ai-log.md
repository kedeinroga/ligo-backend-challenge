# AI log: what I asked the agent and what I corrected

Agent: Claude Code. Workflow: specs in `CLAUDE.md`, plan written with `/challenge-plan`, attacked in a
fresh session with `/validate-plan`, implemented step by step with `/implement-plan`
(skills in `.claude/skills/`). Each entry records a point where the agent's output was wrong or
not fit for this problem, and how it was corrected.

| # | Area | What the agent produced | Why it was wrong here | Correction |
|---|---|---|---|---|
| 1 | Idempotency | An HTTP interceptor backed by Redis: `SET NX` lock with a 30 s TTL, the stored response replayed for 24 h, and the key **released on any error** so the client could retry. | Exactly the double charge of the central question: on a provider timeout the charge may have happened, the key is released, the retry is treated as new and charges again. Also: Redis was the only source of truth (an evicted or lost key reopens the door), the lock had no owner (a slow provider call outlives the TTL and a second pod takes the key; `complete` then overwrote it with a non atomic GET + SET), and the key was not scoped per user. | Removed the interceptor and the Redis store. Idempotency moved to the application layer with MongoDB as source of truth (unique index per user and key). Once the provider may have been called the key is never released: an unknown outcome stays pending and is resolved by a retry with the same key, the webhook or the reconciler. Rule 5.3 in `CLAUDE.md`. |
| 2 | Architecture | A base project with Event Sourcing, a RabbitMQ publisher and Redis, prepared before the statement was known. | The statement asks for a small, well explained solution. Event sourcing made the critical parts harder for no gain in the rubric: completing the operation and crediting the wallet are two streams (no atomic multi stream append), and the reconciler needs "operations stuck in pending", which an in-process projection can lose on a crash. RabbitMQ and Redis had no consumer or need in this flow. | Measured the cost per requirement and chose versioned documents with DDD aggregates and Mongo transactions. Removed event sourcing, RabbitMQ, Redis and every unused config key, port and test, so nothing in the repo is a template leftover. Event sourcing is discussed as an evolution in the README. |
| 3 | API contract | Engineering rules that made amounts decimal strings at every boundary and rejected a JSON number for money with a 400, plus URI versioning (`/v1`). | The statement's contract is binding: `POST /cash-in` with `"amount": 100.00` and `"new_balance": 350.00` as JSON numbers. | Rules rewritten (`CLAUDE.md` section 7): exact paths with no version prefix, JSON numbers validated to at most 2 decimals and converted to `Money` through their decimal string, never through float arithmetic. |
| 4 | API contract | `new_balance: null` in the response for `pending` and `failed` operations. | A `null` balance reads as "balance is zero / unknown" to a client, and the live balance is not stable for replays of the same key. | `new_balance` is present only when `status` is `completed`, taken from the balance stored on the operation at credit time (plan D7). |
| 5 | Error handling after the charge | Plan: on an unknown provider outcome, release the lease and answer 202; a failure while releasing it, or a non concurrency failure while settling an approval, propagated as 500 / 404 / 409. | After the provider may have charged, a 5xx or 4xx tells the client the cash-in failed, inviting a new key (a second charge). | Caught by `/validate-plan` in a fresh session: once the provider was called, `POST /cash-in` only answers 200 (final) or 202 (pending, retry with the same key); every later failure is logged with its cause. Unit tests added for both paths. |
| 6 | Delivery | Plan: reject the default webhook secret when `NODE_ENV=production`. | `docker-compose.yml` runs the api in production mode: the evaluator's `docker compose up` would not boot. | Caught by `/validate-plan`: compose sets an explicit demo secret and the signing script uses it. |
| 7 | Proof of multi pod idempotency | Plan: the "5 requests share a key" e2e ran against one app instance; the lease was described as the exclusivity guarantee. | One instance cannot prove the absence of in-process state, and the lease depends on the pod clock. | Caught by `/validate-plan`: the e2e spreads the requests over two app instances; the plan states the lease only saves provider calls, while safety comes from the provider idempotency key, versioned settlement and the unique ledger id. |
| 8 | Test reliability | Plan: e2e files in parallel on one database, reconciler claiming any stale operation, a 150 ms window for the early webhook test, per pod rate limit active. | Flaky tests: cross file interference, a webhook test that could pass without the webhook arriving first, 429s under bursts. | Caught by `/validate-plan`: sequential e2e files, per test users, explicit `applied` assertion on the early webhook, wider in flight window, high test throttle limit. |
